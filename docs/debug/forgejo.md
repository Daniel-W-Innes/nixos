# Forgejo specifics that decode symptoms


- Forgejo uses a podman postgres container (`forgejo-db`) via a unix socket at `/run/forgejo-db`. The module's preStart runs `forgejo migrate`, which fails fast when the socket is absent and burns the start-limit in ~2s — the unit stays failed even after the DB recovers (2026-09-11; fixed in `generic/server/forgejo.nix` with a `mkBefore` psql wait + `TimeoutStartSec=600`).
- **Dependency-fail = permanent down (2026-09-27, ~40h outage):** if `podman-forgejo-db.service` itself *fails* at boot (podman contention: conmon exit-file ENOENT, boltdb `database is locked` on state save → exit 126), `Requires=` cancels forgejo's start job with `result 'dependency'` — and systemd never re-queues a dependency-failed job. The DB's own `Restart=` recovers ~22s later but nothing re-triggers forgejo: it stays down until someone manually starts it. Fix: `upholds=` beside `requires` in `forgejo.nix` (committed `cf9faf0`, deployed 2026-09-27; reboot verification pending). The 09-11 psql wait-loop only guards a *slow* DB, not a *failed* DB unit. Full report: `docs/reports/2026-09-27-forgejo-dependency-outage.md`.
- Decoder gotcha: when forgejo never starts it emits **zero app lines**, and its unit-lifecycle lines (start/fail/dependency) carry no `unit` label — they're systemd job messages in `init.scope`. Read its state via `{service_name="systemd-journal"} |= "forgejo.service"`, not `{unit="forgejo.service"}` (that stream only carries the app's stdout, which here never happened).
- **Postgres dirty shutdown every boot**: `podman stop`'s default 10s timeout SIGKILLs postgres before its ~16s fast shutdown finishes — the next start logs `database system was not properly shut down; automatic recovery in progress`. Fixed with `extraOptions = [ "--stop-timeout=90" ]` on the DB container (2026-09-27, `docs/issues/12-postgres-unclean-shutdown.md`). If you see postgres crash-recovery lines at boot, this — or a mid-run SIGKILL during a boot storm — is why. WAL replay makes it safe, but it shouldn't be routine.
- Runner 503s (`gitea-runner-*` — `fail to invoke Declare` / `failed to fetch task`: "unavailable: 503") mean traefik is up but the forgejo backend is down. melon's runner crash-loops (exit-code every ~2.5s) and needs a manual `systemctl start` after forgejo recovers — `reset-failed` first if the crash-loop burned the start-limit (`start-limit-hit`); onion's keeps retrying and self-heals.
