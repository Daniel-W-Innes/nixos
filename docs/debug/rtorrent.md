# rTorrent and Flood specifics that decode symptoms

- `rtorrent.service` is confined to the `proton` VPN namespace like transmission (`systemd.services.rtorrent.vpnConfinement`, `generic/server/arr.nix`): it `BindsTo=proton.service`, so when the tunnel dies rtorrent stops with it, and it restarts (reloading its session from `/var/lib/rtorrent/session`) on every Proton restart.
- The SCGI socket `/run/rtorrent/rpc.sock` lives in `/run`, which the network namespace does **not** isolate — that is the whole trick. Flood and `prometheus-rtorrent-exporter` run in the host namespace and reach rtorrent through this socket (group `rtorrent`, `g+w` — see `ls -l /run/rtorrent/rpc.sock`). If either logs EACCES/connection refused on the socket, check the socket's group/permissions and the unit's `SupplementaryGroups`.
- `flood.service` (127.0.0.1:3002, traefik `flood.lc.brotherwolf.ca`) serves rtorrent with `--auth=none`; authentication is traefik's `flood-auth` basic-auth middleware (`/run/traefik-flood-htpasswd`, secret `flood-password.age`). A 401 on the UI is traefik auth, not flood. Transmission keeps its own web UI — flood does not manage it.
- rtorrent's peer port 51821 is opened in the namespace firewall via `openVPNPorts`, but **Proton forwards one port per WireGuard session and transmission (51820, NAT-PMP) holds it**, so inbound peers on 51821 will not arrive — rtorrent runs effectively outbound-only until forwarding is rearranged. Slow/stalled torrents with zero inbound connections is expected, not an incident.
- `configText` in `generic/server/arr.nix` overrides the module's private-tracker defaults (dht on + bootstrap nodes, pex, udp trackers, ratio-stop schedule); the module template runs first, so these win.
- **DHT gotchas (all source-verified against rakshasa 0.16.11 / libtorrent):** `dht.mode.set = auto` only starts DHT from `DownloadList::resume()` — session recovery at daemon boot — torrents added to a *running* daemon never trigger it, so a trackerless magnet fails immediately with "No DHT nodes available for peer search" (the errored arch ISO, 2026-11-12). `on` starts DHT at boot (`load_dht_cache`) and has no auto mode's 15-minute idle auto-stop. libtorrent has **no built-in bootstrap routers** — `dht.add_node` entries (or a warm `session/rtorrent.dht_cache`) are required for the first bootstrap, and the syntax is `host:port` (the comma form on old wiki pages silently resolves the whole "host,port" string as a hostname and fails). DHT binds UDP on the peer port (51821) by default — already covered by the `openVPNPorts` entry.
- rtorrent logs to `/var/lib/rtorrent/log/<timestamp>.log` (its own file, not the journal — Loki won't see it). Expected DHT noise there: "listening port appears to be unreachable/firewalled" (normal under Proton's single forward — inbound DHT never arrives). Success is "DHT bootstrap complete, have N nodes in N buckets." After a config change the errored torrent usually self-recovers on its next announce; re-add it in flood if still stuck.
- Seeding policy mirrors transmission: `group.seeding.ratio.*` values + the `on_ratio` schedule close torrents at 5.0 ratio (upload floor zeroed, so small torrents stop too) — the shipped `group.insert = seeding,seeding` machinery, started directly rather than via the legacy empty-arg `ratio.enable =` idiom. Remove the `schedule2` line in `configText` to seed indefinitely.
- Flood requires `method.redirect = load.*` / `method.insert = d.down.sequential` aliases in the rc (also in `configText`) to expose add-torrent commands in rakshasa/rtorrent > 0.15.1's command map. Without them every add fails instantly with `POST /api/torrents/add-urls 500` while listing still works (2026-11-12).
- Flood itself writes add-torrent destinations on `/mnt/media` (`fs.promises.mkdir(destination)` in its add path) — `flood.service` needs the `media` group as well as `rtorrent`.
- Metrics: `rtorrent_up{job="rtorrent"}` (exporter → socket) and the host-side process count `namedprocess_namegroup_num_procs{groupname="rtorrent"}`. Two alerts: `rtorrent-scrape-failing` (socket unreachable — daemon dead/wedged or socket perms) and `rtorrent-exporter-down` (exporter process itself). `rtorrent_up` is absent when the exporter is down, so check `up{job="rtorrent"}` first.
- Downloads land in `/mnt/media/downloads` (shared with transmission, owned `media`); session/watch/logs live under `/var/lib/rtorrent`.
