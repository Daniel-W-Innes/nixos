# AudioMuse-AI specifics that decode symptoms


- Topology: rootful podman units `podman-audiomuse-postgres`, `-flask`, and `-worker-1..N` (N = `services.audiomuse.workers`, default 2 — the image runs exactly one default-queue worker per container, one album at a time; upstream's k8s manifest scales the same worker pod ("Scale as needed"), dispatch throttle MAX_QUEUED_ANALYSIS_JOBS=25 caps how many replicas matter; 2026-10-17 measurement: ~45s/track single-stream ≈ 3 weeks for 3688 albums, hence the replicas — but ONNX inference is multi-threaded per replica, and 4 of them oversubscribed the 64 cores (load ~73), so the default is 2) on the dedicated bridge `audiomuse-net` (created by `init-audiomuse-network.service` with `--subnet 10.89.1.0/24` pinned, bookorbit pattern — no host networking anywhere). **Remote worker (2026-10-19):** onion runs one more replica, `podman-audiomuse-worker-1`, via the module's `workerOnly` role (`generic/desktop.nix` sets `postgresHost = "melon"`, `postgresPort = 5433`) — no postgres/flask/audiomuse-net on onion, the worker just makes outbound connections to melon's postgres on the default podman bridge, so melon's firewall DNS trap (below) does not apply to it. `melon` resolves via the router's DHCP-lease DNS (10.8.8.1) — that is what the worker container and the probe use; **`melon.local` would NOT work from the container** (containers have no mDNS; `.local` is multicast-only, resolvable on hosts via avahi). The name auto-tracks melon's DHCP lease, unlike a static `.lc.brotherwolf.ca` entry. Its `ExecStartPre` is a full **mTLS psql login** (cert + scram + `select 1`) after `network-online.target`; `Restart=on-failure` requeues if melon is down at boot. Host publishes on melon: `5433` (postgres, all interfaces — but the custom pg_hba below denies everything except the app containers, melon loopback, and mTLS clients on the home LAN, so the exposure is an open port, not an open door) and `127.0.0.1:8000` (flask gunicorn, binds 0.0.0.0 in-container so the publish works). 5433, not 5432: the dawarich module enables host postgresql which owns `127.0.0.1:5432` — a 5432 publish makes the unit crash-loop on `bind: address already in use` (2026-10-17 first deploy). Traefik proxies `127.0.0.1:8000` as `audiomuse.lc.brotherwolf.ca` (internal-only). Postgres data: `/var/lib/audiomuse/postgres` **must stay 70:70** (`postgres:15-alpine` uid; tmpfiles `d` rule — see `docs/issues/14-forgejo-tmpfiles-ownership-mismatch.md`; a wrong uid breaks every new connection on `global/pg_filenode.map` and postgres refuses to start on a wrong-ownership dir).
- **mTLS on the DB (2026-10-19):** postgres runs with `ssl=on` via `cmd` `-c` flags; the container mounts a custom `pg_hba.conf` (a `pkgs.writeText` store path at `/pg-hba/pg_hba.conf`) and `/var/lib/audiomuse/pg-ssl` (populated by the postgres unit's `ExecStartPre` `installPgSsl` before every start: server.key 0600 uid 70 from agenix, certs from the store). hba sources: `local … trust` (container socket — the image's temp server and `podman exec psql`), `host 10.89.1.0/24 scram` (app containers; subnet pinned at network creation), `host 127.0.0.1/32 scram` (host-side pg_isready wait + debugging), `hostssl 10.8.8.0/24 scram clientcert=verify-full` (mTLS workers on the home LAN — the /24 avoids pinning onion's DHCP address; pg_hba can't match DNS names, and the client cert + scram are the real gate anyway). Everything else is denied, so DB admin work happens on melon via `127.0.0.1` or `podman exec`. The worker container gets `PGSSLMODE=verify-full` + `PGSSLROOTCERT/PGSSLCERT/PGSSLKEY` env (psycopg2/libpq honors them; mounted under `/pg-client`). Cert material: public certs are plain files in `generic/server/audiomuse-pg-certs/` (server cert SAN `DNS:melon` primary, plus `DNS:melon.local`, `IP:10.8.8.140`, `IP:127.0.0.1`, `DNS:audiomuse-postgres`), private keys are `audiomuse-pg-{server,client}-key.age`; regenerate with `scripts/gen-audiomuse-pg-certs.sh` (10y validity, client cert `CN=audiomuse` — required by verify-full). **Rotation:** regenerate + re-encrypt the two keys + restart `podman-audiomuse-postgres` and `podman-audiomuse-worker-1` (agenix secret edits do not restart containers, CLAUDE.md gotcha). Symptom map: worker crash-loop with `SSL error`/`certificate verify failed` = cert mismatch or expired; `pg_hba.conf rejects connection` in postgres logs = source not in the hba list.
- App caches: `/var/lib/audiomuse/flask/{temp-audio,plugins}` and `/var/lib/audiomuse/worker-<n>/{temp-audio,plugins}` per replica (root-owned, container runs as root). Temp audio and the plugin pip cache are per-container on purpose (upstream compose shape; k8s PVC-per-pod) — they are caches, safe to clear, but re-installing plugin deps costs analysis time.
- Secret: `/run/agenix/audiomuse-env` (one line `POSTGRES_PASSWORD=...`), consumed via `environmentFiles` by all containers incl. onion's worker (rekeyed for every host's system key, no secrets.nix change needed). **Editing it does not restart the containers** (CLAUDE.md gotcha) — on melon `systemctl restart podman-audiomuse-postgres podman-audiomuse-flask 'podman-audiomuse-worker-*'`, on onion `systemctl restart podman-audiomuse-worker-1`. `POSTGRES_PASSWORD` only seeds initdb: rotating the file alone does not change the live DB — also `ALTER USER audiomuse PASSWORD '...'` (via `podman exec audiomuse-postgres psql -U audiomuse -d audiomusedb`).
- Startup: `dependsOn` gives ordering only, not readiness. Flask runs `init_db()` at import and supervisord abandons it after 3 quick retries, so a slow DB wedges the container "Up" but broken. The flask and each worker-<n> unit carry an `ExecStartPre` pg_isready wait (90s, host-side over the published port) and `upholds=` on the postgres unit (dependency-fail re-queue, `docs/reports/2026-09-27-forgejo-dependency-outage.md`). If the UI 500s while the container is up, look for supervisord `FATAL` in `podman-audiomuse-flask` logs.
- **Wizard URL trap:** the setup wizard asks for the Navidrome URL and the AudioMuse server (flask container) calls it server-side. From the bridged container the host loopback is unreachable — `http://127.0.0.1:4533` fails with connection refused. Use **`https://navidrome.lc.brotherwolf.ca`** (traefik; container egress SNATs to the host LAN IP, which `internal-only` allows; the image has ca-certificates). The reverse hop — the Navidrome plugin's `apiUrl` — runs from the host side, so there it **is** `http://127.0.0.1:8000`. Don't mix these up.
- Navidrome plugin: baked into the navidrome package (`services.navidrome.plugins` in `generic/server/arr.nix`; plugin settings live in navidrome.db, enabled/configured in UI → Settings → Plugins). `Agents = "audiomuseai,lastfm,deezer"` — **audiomuseai must be first** (Navidrome uses the first agent with sonic-similarity support) and replaces the default `deezer,lastfm,listenbrainz` (listenbrainz agent dropped; lastfm/deezer inert without keys). If Instant Mix falls back to non-AudioMuse behaviour, check `Agents` and the plugin's enabled state.
- Jellyfin plugin: `audiomuse-ai-plugin` v0.3.5 (targetAbi 12.0.0.0 = jellyfin 10.11), symlinked into `/var/lib/jellyfin/plugins` by tmpfiles `d`/`L+` rules (`generic/server/arr.nix`); `restartTriggers` restarts jellyfin when the plugin package changes — if the plugin is missing after the first switch, `systemctl restart jellyfin`. Jellyfin may auto-update the plugin from its catalog manifest, writing a real file beside the symlinks; the managed store copy wins again on the next switch. If Instant Mix misbehaves right after an upstream plugin release, check `ls -la /var/lib/jellyfin/plugins`.
- **Multi-server naming gotcha:** AMA's plugins send an optional `server` param; without it the API hits the **default** server. Navidrome is the default (first wizard server), so its plugin can leave `server` blank — but the Jellyfin plugin **must** set Media Server Name to whatever the Jellyfin server is called in AMA's Music Servers page, or its Instant Mix will return Navidrome-relative results. Plugin 401s with the Jellyfin plugin = same token mismatch as Navidrome.
- AMA ↔ Jellyfin backend: add the Jellyfin server on the AMA **Setup page** (admin-only after first setup): type Jellyfin, URL **`https://jellyfin.lc.brotherwolf.ca`** (same bridged-container trap — host loopback is unreachable from the flask container, go through traefik), a Jellyfin **user ID + API key** (created in Jellyfin dashboard → API Keys), optional library filter. A Jellyfin **Music** library must exist or there is nothing to scan. Analysis then processes every configured server sequentially (default first); tracks shared with Navidrome are content-hash-deduped, so the Jellyfin pass mostly adds mappings — use "Align music servers" for instant metadata-only matching.
- Plugin 401s = API token mismatch between the plugin config and the wizard token. No requests reaching AudioMuse logs = wrong `apiUrl` (loopback is correct from Navidrome's side) or plugin disabled. Empty/weak results = analysis not run/complete yet — run the full library analysis in the AudioMuse UI and let the workers finish (CPU-heavy first pass; `journalctl -u 'podman-audiomuse-worker-*' -f`, or `podman logs audiomuse-worker-1` for one replica). `PER_SONG_MODEL_RELOAD=false` is set on the workers — upstream's default reloads both MusiCNN ONNX models after every song to bound VRAM leaks, pure overhead on CPU-only.
- **Version drift is upstream's #1 error source**: keep the core image, the plugin (`audiomuseai.ndp` in `arr.nix`), and Navidrome aligned. The image is `:latest` with podman's default `pull = "missing"` — a rebuild does **not** update it: `sudo podman pull ghcr.io/neptunehub/audiomuse-ai:latest` then restart **both** `podman-audiomuse-flask` and `podman-audiomuse-worker` together. Bumping the plugin = new `hash` + version in `arr.nix`.
- Backups: none configured for `/var/lib/audiomuse/postgres`. Analysis is regenerable but expensive; consider a `pg_dump` timer before doing anything destructive.
- **The firewall DNS trap (2026-10-17 incident):** the host firewall (`networking.firewall`, nftables backend) must let containers reach aardvark-dns on their bridge's gateway IP; `generic/podman.nix` originally allowlisted only `podman1` (bookorbit-net), and `audiomuse-net` is `podman2` — every lookup from the app containers was silently dropped. Symptom: `could not translate host name "audiomuse-postgres": Temporary failure in name resolution` in the app containers (gunicorn crash-loop; worker fallback logs that look like success), while host-side `dig @10.89.1.1 audiomuse-postgres` answers fine — the firewall's `input` chain (policy drop; `input-allow` has no podman2 rule) runs before netavark's own INPUT accepts. Fix: wildcard `extraInputRules = [ ''iifname "podman*" udp dport 53 accept'' ]` in `generic/podman.nix`; ephemeral equivalent: `nft add rule inet nixos-fw input-allow 'iifname "podman*" udp dport 53 accept'`. Any new podman bridge hits this again silently — check the firewall before suspecting podman.
- **`podman network rm --force` can leave a ghost (2026-10-17 incident):** audiomuse-net teardown errored mid-way (`netavark: no static ips provided`, exit 125) — IPAM/state partially removed but netavark's nftables cleanup never ran. The dead network's chains (`nv_68f0bfed_*` in `table inet netavark`) kept a hostport jump for `127.0.0.1:5433` ahead of the live network's, DNATing every connect to the dead container IP: `pg_isready` "no response"/SYN-SENT while `ss` shows LISTEN, `ip neigh` FAILED on the ghost, and a stale `/run/containers/networks/firewall/ports/<deadnetid>_*` file on disk. Fix: delete every rule+chain referencing the dead network id by handle (`nft -a list ruleset`, awk for `# handle N` lines), confirm zero mentions, then check the surviving DNAT targets the live container IP (top-level `.NetworkSettings.IPAddress` is empty for named-network containers — use `{{range $k,$v := .NetworkSettings.Networks}}{{$v.IPAddress}}{{end}}`) and `podman network reload` the container if it lags.
- First-boot race noise: while flask's initial schema migration runs (~2 min after first healthy start), the worker's maintenance cycle errors `relation "task_status" does not exist`; it self-heals on the next cycle — ignore unless it persists after `/api/health` returns 200.
- **ghcr.io pulls crawl on melon (~70 KB/s, 2026-10-17) but run fast on onion (~53 MB/s).** For the audiomuse image: pull on onion (`skopeo copy docker://ghcr.io/neptunehub/audiomuse-ai:latest docker-archive:/tmp/audiomuse-ai.tar`), ship the tarball to melon, `sudo podman load -i` there. (Not the CLAUDE.md grafana-403 org block — neptunehub pulls anonymously, just slowly.)
- **Switch-time bounce (Upholds cascade, 2026-10-19):** flask and the melon workers declare `Upholds=podman-audiomuse-postgres.service`, so **any melon switch that restarts the postgres container also restarts the app containers** — the whole stack bounces for ~2.5 min (stop 21:35:48 → UI healthy 21:38:14 on the mTLS deploy). This is by design, not breakage: "audiomuse down right after a melon switch" + all units active within ~3 min + `/api/health` 200 = the bounce. In-flight album tasks are SIGTERMed mid-track; the queue requeues them (the `MainAnalysisTask` restarts its album counter but already-analyzed tracks are skipped, and its retry budget is 4 attempts — if it eventually fails, re-trigger it in the UI). Note the byte-identical `waitForPostgres` binding exists so melon switches that DON'T touch postgres don't restart the app containers at all.
- **Worker probe hang when melon is unreachable (2026-10-19 incident):** the onion worker's `ExecStartPre` mTLS probe assumes fast connection failures, but melon's firewall **drops** 5433 (not in `allowedTCPPorts`; the published port only works through netavark's DNAT once melon is switched) — DROP means each `psql` attempt hangs for the full TCP timeout, so the original 90-iteration loop wedged the unit in `start-pre` for hours during activation. Fixed with `PGCONNECT_TIMEOUT=5` + 30 iterations (≤ ~3 min bound); `Restart=on-failure` then retries until melon is up. Symptom: `switch-to-configuration` appears hung + `systemctl list-jobs` shows `podman-audiomuse-worker-1.service start running` with `SubState=start-pre` — check `ss -tlnp | grep 5433` on melon (loopback-only = melon not switched yet; switch melon first, then onion).
