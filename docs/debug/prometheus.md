# Prometheus playbook (mcp-grafana)


- **Aggregate before you pull.** One number per series beats hundreds of samples:
  - LAN/upstream health: `min_over_time(up{instance=~"onion.*"}[3h])` (4 numbers) instead of a 60 s-step range dump (~700 points).
  - Signal baseline: `sum(count_over_time({service_name="systemd-journal"} |~ "(?i)gaierror" [10m]))` as a range query, step 600 — shows whether an error is constant noise in one call.
- melon = `localhost:*` instances; onion = `onion.lc.brotherwolf.ca:*` (9100 node, 9256 process, 9633 smartctl, 9835 nvidia, 12345 alloy since 2026-09-04 — bound to LAN with pprof off; the alloy UI is served there too, no auth). onion scrapes at 60 s cadence are the cheap LAN-health probe.
- Provisioned Grafana alerts (group `visibility`, folder visibility, all → gotify): `traefik-backend-down`, `traefik-backend-down-1h` (companion, see next bullet), `traefik-down`, `alloy-down`, `alloy-shipping-failing`, `transmission-down`, `wireguard-exporter-down`, `wireguard-handshake-stall` — eight rules in `generic/server/visibility.nix`. Equality conditions must use `== bool 0`: a bare `== 0` *filters* series instead of yielding 1 and can never fire (fixed 2026-09-19 — the broken `transmission-down` silently masked a 28 h outage, see `docs/reports/2026-09-18-transmission-wedge.md`). `>`-style conditions are fine as-is.
- **Grafana-managed rule state resets when Grafana restarts** (2026-09-27): `activeAt` re-stamps, so a 40h-old outage looks 3 min old after a reboot, and phantom "blips" appear for other services as their alert path hiccups across the restart (gotify showed a 10:15 "blip" whose metric never moved: `changes(...[24h])` = 0). Judge onset from the underlying series (`traefik_service_server_up{service=~".*@file"}` range), never from `activeAt`. Fixed with the companion rule `traefik-backend-down-1h` (`max_over_time(traefik_service_server_up{service=~".*@file"}[1h]) == bool 0`, `for = "0m"`): its 1h window lives in Prometheus data, survives Grafana restarts, and never trips on blips — when it fires, the outage is genuinely ≥1 h old. See `docs/reports/2026-09-27-forgejo-dependency-outage.md` §7.3.
- Key devices on melon's node_exporter: `ens3` (the only NIC — LAN+WAN), `proton-br` (VPN bridge — only VPN-ns traffic visibility; healthy keepalives are a *flat* ~51 B/s tx / ~367 B/s rx when idle, 2026-09-19 regime — the old "100–800 B/s" figure is wrong, so judge dead-ness by collapse from that host's own baseline, not an absolute threshold). Since 2026-09-05 the in-ns wireguard exporter (`job="wireguard"`, `wireguard_latest_handshake_delay_seconds`) is the first-class tunnel signal; `wireguard-handshake-stall` fires when every peer's handshake is >300 s old. **Handshakes prove the control plane, not the data plane**: the 2026-09-18 outage had handshakes ≤138 s while the path-MTU shrink blackholed payloads (`docs/issues/done/09-transmission-start-wedge.md`). 5-min `rate()` smears short events — a 10 min outage shows as ~zero rates at the 5-min samples spanning it.
- `process_exporter` namegroups exist on melon (23 groups) and onion since `docs/issues/done/02-process-exporter-namegroups.md` — e.g. `namedprocess_namegroup_num_procs{groupname="transmission"}`. That's a process-count series, not an RPC health check: it was 1 during the 2026-09-18 wedge's start attempt while RPC hung.
- Hourly iperf3 speed tests run from the melon `iperf-probe` systemd timer (nixpkgs iperf3) into the node_exporter textfile collector — `iperf3_*{target=...,port="5201"}` appear under `job="node_exporter"`, `instance="localhost:9100"`. Replaced the segfaulting container exporter 2026-09-05 — `docs/issues/done/04-iperf3-exporter-segfault.md`.
