# Lidarr specifics that decode symptoms

- Service: `lidarr.service` on melon, `ExecStart` = `Lidarr -nobrowser -data='/var/lib/lidarr/.config/Lidarr'` (Lidarr 3.1.0.4875), `User/Group=lidarr`, `Restart=on-failure`, `LIDARR__SERVER__PORT=8686`, auto-update off (`UPDATE__MECHANISM=external`). Config: `generic/server/arr.nix` (shared minimal arrSettings — no resource limits, no port/DB tuning). State dir is 0700 root — lidarr.db size/WAL state and logs need root. Traefik router `lidarr@file` at `lidarr.lc.brotherwolf.ca` with a `/ping` healthcheck every 10 s (`generic/server/traefik-targets.nix`).
- API consumers (who puts load on the 8686 API): **exportarr-lidarr** (`prometheus-exportarr-lidarr-exporter.service`, `URL=https://lidarr.lc.brotherwolf.ca` through traefik, key from `lidarr-api-key.age`) — a **full collection every Prometheus scrape**: every page of `/api/v1/queue` plus `/api/v1/artist` etc. The global `scrape_interval = "10s"` applies with no per-job override (`generic/server/visibility.nix` ~line 709/919), and exportarr 2.3.0 exposes **no collector-disable flags** (only `--enable-additional-metrics`, `--enable-unknown-queue-items`, auth/URL/port) — interval or stop are the only levers. Traefik `/ping` every 10 s. `lidarr-search-drip` every 4 h at :17 (Persistent=true → fires immediately after a switch; ~13 paginated `/api/v1/wanted/missing` queries + one AlbumSearch of 25; `RuntimeMaxSec=1800`, `--max-time 60`). `lidarr-mcp` on onion (on-demand, full CRUD). `mixarr` (only if the user configured Lidarr in its UI — the repo passes it no Lidarr URL/key).
- **"Stuck on loading screen" = the SPA shell loaded but an API call hangs** — the shell and `/initialize.json` return in ms, then the SPA blocks on `GET /api/v1/artist` (or `/api/v1/queue`). The user's browser eventually aborts → traefik 499 rows with 100–460 s Durations. `/ping` stays green the whole time (light endpoint), Kuma never fires Failing, no alert fires — the failure is latency, not liveness. The 2026-11-02 signature: `/api/v1/artist` p50 **1,289 s** (baseline 1.4–4.7 s) while `/ping` = 200 in 1.6 ms.
- **The mechanism (2026-11-02 incident, `docs/reports/2026-11-02-lidarr-loading-screen.md`):** big queue × exportarr's full pagination = self-sustaining saturation. Queue ~2,740 items (**137 pages**) after a 2026-10-30 import storm (1,843 albums) → every 10 s sweep is 137 queue-page calls + the 1.8 MB artist payload → 474–606 req/min through traefik, 315+ ESTAB to `:8686`, Lidarr RSS 16+ GB / ~345 threads → hourly `database is locked` 420–851 (baseline ≤245) → `[Fatal] Request Failed GET /api/v1/queue` clusters (284 in one day) → SPA artist calls starve. The lock storm can end while the pileup persists — requests then take 20+ min, not fail.
- **Decisive checks (cheapest first):** ① `ss -tan | awk '$1=="ESTAB" && $4 ~ /:8686$/ {c++} END{print c+0}'` on melon (noise: tens; outage: 300+). ② `journalctl -u prometheus-exportarr-lidarr-exporter -n 20` — a live flood shows `Sending HTTP request .../api/v1/queue?page=<N>` lines with many pages per second. ③ Loki: `count_over_time((up{job="exportarr",instance="localhost:9710"}==0)[24h:1m])` vs `offset 24h` (265 vs 4 on the incident day); traefik latency `sum(rate(traefik_service_request_duration_seconds_sum{service="lidarr@file"}[5m]))/sum(rate(..._count[5m]))`. ④ Lock baseline: `sum(count_over_time({hostname="melon", unit="lidarr.service"} |= "SQLite error (5): database is locked" [1h]))`. ⑤ Who hit what: traefik `DownstreamStatus` by `ClientHost` for `lidarr@file` — `.140` is melon/exportarr, `.188` is the user; user 499s + zero 503s = the loading screen, exportarr-only 503s = connection saturation.
- **Recovery order matters: stop the exporter FIRST, before any lidarr restart** — restarting lidarr mid-flood just rebuilds the pileup. `systemctl stop prometheus-exportarr-lidarr-exporter`, wait 5–15 min for the backlog to drain (watch the ESTAB count fall toward 0 and RSS fall), then reload the UI. Only if still wedged after the drain: `systemctl restart lidarr` (safe once locks are 0). 2026-11-02 numbers: 315→2 ESTAB and 16.3→11.2 GB RSS within minutes of the stop; script pattern at `/tmp/lidarr-relief.sh` on melon (stop / `--check` / `--restart-lidarr`). The exporter unit is **currently stopped** on melon post-incident — exportarr-lidarr metrics are absent until re-enabled, expected, not a new outage.
- **Not this:** crash/restart (check `systemctl show lidarr -p NRestarts` — 0 since Oct 8 on the incident day), disk full, OOM, traefik route down (light endpoints answer in ms), CIFS stall, the other arr apps (sonarr/radarr/prowlarr healthy while lidarr starves), mixarr (195 req/24 h) or blunderbase/maia (chess, `/health` only). `lidarr-search-drip` timing out (`curl: (28) Operation timed out after 60001 ms`, exit 28) is a **victim** of the stall, not a cause. Traefik `lidarr@file` healthcheck blips are the chronic noise class (`docs/debug/known-noise.md`) and look different: brief `server_up=0` with short 503s — the exportarr stall keeps `server_up=1` throughout.
- **Lock bursts are noise only while the queue is small** — the `*arr` line in `docs/debug/known-noise.md` says so and is conditional on that. With a 100+ page queue the same mechanism is the outage. Also: the docs' EDT (UTC−4) anchor went stale after the 2026-11-01 DST change — journal times are EST (UTC−5) since.
- **Fix (working tree, pending deploy, 2026-11-02):** exportarr job `scrape_interval = "5m"` in `generic/server/visibility.nix` (was the global 10 s); all four `exportarr-*.url` → loopback ports (8686/8989/7878/9696, keeps the sweeps off traefik); `exportarr-scrape-down` alert (`up{job="exportarr"} == bool 0`, `for = "15m"` — mind the `== bool 0` gotcha in `docs/debug/prometheus.md`). Tracking issue: `docs/issues/11-lidarr-cpu-spin.md` — this class *is* its thread-pool starvation, mechanism now identified.
