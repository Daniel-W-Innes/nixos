# Transmission specifics that decode symptoms

- `transmission.service` runs in the `pia` VPN namespace (vendored `vpn-confinement` module with OpenVPN transport, `generic/server/arr.nix`, `modules/vpn-confinement/`). Units: `vpn-confinement-netns@pia.service` builds the netns (nftables drop-policy, veth hostLink, openvpn endpoint exemption), `vpn-confinement-openvpn@pia.service` runs openvpn inside it (`Restart=always`, ping-restart 120 → the tunnel self-heals; a crash does **not** touch transmission), and transmission binds to both. The tunnel is `pia0` (tun) in the netns; the hostLink is veth `vh-f54ccddff8d3` (host side, 169.254.140.41) ↔ `vn-00b8ef1b6bc7` (ns side, 169.254.140.42) on subnet 169.254.140.40/30, all derived from the namespace name.
- **There is no port DNAT.** The RPC binds `169.254.140.42:9091` inside the namespace; the host reaches it directly over the veth route (`publishToHost.tcp = [9091]`), so traefik (host process) targets `rpc-bind-address:rpc-port` as before. `localhost:9091` and LAN `10.8.8.140:9091` are connection-refused — expected, not a symptom (the old proton setup DNATed wire traffic; this one doesn't). From melon: `curl -m 5 http://169.254.140.42:9091/transmission/rpc` → 409 = daemon answering; 401/403 = answering but refusing auth.
- Restart semantics: openvpn crash → `Restart=always` on the tunnel unit auto-restarts it **without touching transmission** (auto-restarts don't propagate PartOf/BindsTo; verified 2026-11-22), so transmission's TCP connections stall ≤2 min and recover — no session reload. An *explicit* `systemctl restart vpn-confinement-openvpn@pia` (or restarting `vpn-confinement-netns@pia`, which tears the namespace down) does propagate to transmission and reloads its ~10 min session, like the old `proton.service` restart.
- Transmission 4.x runs the torrent session, tracker announces, peer I/O, and the RPC server on **one thread**. A blocking network op through the VPN freezes the RPC too → connections *hang* (timeouts), never refuse. A wedged daemon logs nothing (`message-level = 3` only logs errors; blocked ≠ error).
- Tunnel liveness is now observable: openvpn rewrites `/run/openvpn/pia.status` every 10 s and the `openvpn-exporter` serves it to Prometheus (job `openvpn`); the `pia-tunnel-stalled` alert fires when it stops updating for 5+ min. The old `proton-br` keepalive counter is gone with the bridge — the host-side veth (`vh-*`) counter and the status file are the new signatures. Dead tunnel ≠ dead namespace: with openvpn wedged, transmission hangs like the 2026-09-03 class; with openvpn *dead*, ping-restart reconnects in ≤2 min.
- Port forwarding: `pia-port-forward.service` (in the netns, timer every 15 min + on every tunnel connect) calls PIA's PF API on the tunnel gateway (`getSignature`/`bindPort`, credentials + CA extracted from the .ovpn) and writes `/run/pia-port-forward/port`. `pia-port-forward-apply.service` (host) opens that port on `pia0` in the ns firewall and pushes it into transmission via RPC + settings.json. State lives in `/run/pia-port-forward/` (state, port, current — tmpfs, rebuilt each boot). Symptoms to decode: no inbound peers + `systemctl status pia-port-forward` failing = PF broken (wrong region without PF support? server rotation changing the gateway?); port changed but transmission stale = apply failed. Verify: `ip netns exec pia nft list ruleset | grep dport`, `cat /run/pia-port-forward/current`, transmission's peer-port via RPC.
- OpenVPN startup failures land in three known traps (all fixed in the module, all 2026-11-22): (1) the netns script resolves the endpoint with `pkgs.getent` — the pinned nixpkgs moved getent **out of glibc.bin**, so a `glibc.bin` path embeds fine at build time but execs a nonexistent file at runtime (`line N: /nix/store/...-glibc-...-bin/bin/getent: No such file or directory`); (2) PIA's .ovpn ships `ncp-disable`, which openvpn 2.6 no longer parses (`Options error: ... pia.conf:9: ncp-disable`), and bare end-of-line directives (e.g. `auth-user-pass`) survive a trailing-space-only sed filter — the run script strips lifecycle/obsolete directives with `(...)([[:space:]]|$)`; (3) the openvpn client runs **inside the namespace**, so its pre-tunnel traffic egresses the veth with the link-local ns address as source — no upstream router routes replies back to a link-local address, so the TLS handshake blackholes (`TLS Error: TLS key negotiation failed to occur within 60 seconds`, zero inbound packets despite `UDPv4 link remote` being set). The netns unit adds a host-side `inet vpnc-host-<ns>` postrouting masquerade for the ns address (deleted on stop/failed start); postrouting only sees forwarded traffic, so veth-local RPC is unaffected.
- A wedged daemon wedges on *stop* too: `State 'stop-sigterm' timed out. Killing.` → SIGKILL → "Failed with result 'timeout'". So `systemctl restart` on a wedged daemon kills it (fine) — but the replacement can then time out *starting* if the namespace is still rebuilding; issue another start once `vpn-confinement-netns@pia.service` has settled (2026-09-11, see `docs/issues/done/08-forgejo-db-start-race.md`).
- 2026-09-03 reference incident: transmission RPC dead 21:35–21:56 EDT, self-healed, no restart, correlated with the VPN tunnel dying. Full report: `docs/reports/2026-09-03-transmission-outage.md` (was Proton/`proton-br`; the failure class — dead tunnel freezing the single thread — is identical under PIA).
- Boot-wedge signature (2026-09-18/19, resolved — full story `docs/reports/2026-09-18-transmission-wedge.md`, `docs/issues/done/09-transmission-start-wedge.md`): a *start* attempt wedges with the RPC bound (traefik 499s = accepted, never answered; fast 502 = nothing listening) and systemd's 90s start+stop timeouts SIGKILL it. Two stacked environmental causes were found, both from a hypervisor shutdown: (1) **path-MTU shrink** blackholed big tunnel packets — probe the ns directly (`nsenter --net=/run/netns/pia curl -m 10 https://ipinfo.io/ip`): DNS ✓ + TCP ✓ + TLS ✗ = MTU; the knob is now `tun-mtu`/`mssfix` in the `pia-vpn.age` .ovpn config (was `proton0` MTU 1300 under WireGuard); (2) **degraded CIFS session** made every uncached metadata op on `/mnt/media` ~2.5 s, and startup stats ~4000 torrents' files serially — hours vs the 90 s timeout. CIFS decoder: `time stat` on a cold path (want ms); per-thread stacks showing `[cifs] wait_for_response → smb2_query_path_info` = CIFS-blocked (the daemon was *crawling*, never deadlocked — a wedged main thread in `futex_wait` with a worker in `[cifs]` is this). Fix: `systemctl restart mnt-media.mount`. Note: `node_filesystem_avail_bytes` did NOT catch this (warm statfs ≠ cold metadata ops) — the early "CIFS ruled out" ruling was wrong.
- Wedged-start forensics recipe (learned 2026-09-19): (1) run the daemon in the foreground with the netns only (`nsenter --net=/run/netns/pia sudo -u transmission -- <EXE> -f -g /var/lib/transmission/.config/transmission-daemon --log-level=debug`) — if it works there, the sandbox holds the clue; (2) reproduce under the real unit with a drop-in that replaces ExecStart with `--log-level=debug` + `StandardOutput=append:/tmp/...`; (3) during the wedge capture per-thread stacks: `for T in /proc/<pid>/task/*; do cat $T/comm $T/wchan $T/stack; done`. The `[cifs]`/`[ext4]`/etc. module tags in the stack name the blocking filesystem directly.
