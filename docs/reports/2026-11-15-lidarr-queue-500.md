# Lidarr queue API 500s — duplicate monitored release + ghost artist (2026-11-15)

## Symptom

- decluttarr (newly deployed) logged `500 Server Error: Internal Server Error for url: https://lidarr.lc.brotherwolf.ca` on its Lidarr pass. The URL in the user's paste has no path because that's `requests.exceptions.HTTPError.__str__`; the actual failing call (from decluttarr's log) was `GET /api/v1/queue?page=1&pageSize=2905&includeUnknownArtistItems=True`.
- Lidarr journal: `[Fatal] LidarrErrorPipeline: Request Failed. GET /api/v1/queue` in ~5-min clusters. Loki `count_over_time` showed ~30–45/h all week — **pre-existing since well before decluttarr's first start (11:20)**; decluttarr surfaced it, not caused it.
- exportarr-lidarr (5-min scrape, default pageSize) failed on **page 6** of the queue every sweep — pages 1–5 always 200. The queue had ~2,900 items (post-2026-10-30 import storm).

## Mechanism

`QueueResourceMapper.ToResource` calls `SingleOrDefault(x => x.Monitored)` on an album's AlbumReleases. An album with **two monitored releases** throws `InvalidOperationException: Sequence contains more than one matching element`, and every queue page containing that album's tracked download returns 500 (any page containing the item — hence page 6 for exportarr's 20-item pages, and page 1 for decluttarr's single ~2,900-item page).

- Culprit: album 54425 "The Jaws of Life" (Pierce the Veil), releases 141095 (2023-02-10, original) and 141125 (2025-05-09, deluxe) both `Monitored=1`.
- Second failure, same disease: ghost artist "Adèle" (id 589, ArtistMetadata 4352) sharing `CleanName "adele"` with the real Adele (id 642) → `ParsingService.GetArtist` found two artists → `MultipleArtistsFoundException` → three torrents (Adele 30 / 19 / 21) errored every ~5 min since ~2026-11-03 instead of importing. The ghost's path `/mnt/media/music/Adèle` never existed; it held 3 albums (French artist "Adèle": Jazz / Garden partie / Bleu) and 29 tracks, **zero files**.

## Fix (applied live on melon 2026-11-15 ~12:11)

1. `UPDATE AlbumReleases SET Monitored=0 WHERE Id=141125` (kept the original monitored).
2. `DELETE /api/v1/artist/589?deleteFiles=false&addImportListExclusion=false` via Lidarr's API.
3. `systemctl restart lidarr` — **required**: the direct DB `UPDATE` leaves Lidarr's in-memory Album cache stale; probes still 500'd until the restart rebuilt the queue. (If the release had been toggled through the UI/API instead of SQL, the restart would have been avoidable.)

## Verification

- After restart: `queue?page=1/2/6/101` → 200, `queue?page=1&pageSize=3000` → 200, `queue/details?page=1` → 200. totalRecords 2908 → 2899 (ghost artist's items gone).
- decluttarr's next Lidarr pass (12:19): clean, no errors, jobs ran (dry-run removals logged).
- Only post-restart error: one `[Fatal] GET /api/v1/queue` at 12:11:35, 6 s into startup — the probe hit the boot lock storm (`SQLite error (5): database is locked in "PRAGMA cache_size"` lines at the same second); transient, never repeated.
